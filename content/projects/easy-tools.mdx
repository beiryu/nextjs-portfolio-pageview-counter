## Technology Stack

Next.js 16 (App Router), React 19, TypeScript strict, Tailwind CSS 4, shadcn/ui, Base UI, class-variance-authority, tailwind-merge, Lucide, dotLottie, Wistia embeds, self-hosted Borna and Geist webfonts, ESLint, Docker, GitHub Actions, Vercel

## Overview

Duration: 7/2026 - 8/2026

Easytools is a suite for creators selling digital products — a one-page checkout, an AI website builder, email campaigns, a course player, testimonial collection — all sitting on the seller's own Stripe account. Its public site is large: a page per tool, a page per feature, a page per thing you might sell, plus resources and legal.

This project is a reconstruction of that site, front to back, as a modern Next.js codebase: **75 routes, 194 components, 489 downloaded images**, and the authenticated creator dashboard on top of the marketing surface. It is a fidelity exercise rather than a product — the brand, copy and assets belong to Easytools; what is mine is the codebase underneath them and the method that produced it.

That method is the actual subject here. Rebuilding a site this wide by eyeballing screenshots does not converge — the twentieth section drifts from the first. So the interesting work was making the reconstruction *measured* instead of *estimated*.

## Reconnaissance Before Code

The pipeline runs the browser first and the editor second. Each page is opened under Chrome automation, screenshotted, swept for interactions (scroll, click, hover, responsive breakpoints), and interrogated with `getComputedStyle()` — so what lands in the repository is measurements, not impressions.

Those measurements become spec files. `docs/research/components/` holds **58 of them**, one per section, and they read like this:

> H1 — font "Borna Webfont" (bold 700), 56px, line-height 64.4px, base colour `#0E534C`, accent span "ever before" `#00A18B`. Media shell — background `#fff`, `border-radius: 12px`, `box-shadow: 0 0 0 8px rgba(0,0,0,0.05)` (a soft ring, **not** a drop shadow).

Each spec carries the DOM structure, exact computed values, interaction model, multi-state content, responsive behaviour, and asset paths — enough that a section can be built without ever consulting the original again. Sections were then built in parallel, one agent per spec in its own git worktree, and merged back.

The specs also record what *not* to do. The hero spec ends its interaction note with "do not build a fake HTML/CSS app mockup" — the live site swaps a static poster for a Lottie after load, and reproducing the poster is the correct answer. Writing the trap down is what stops a parallel builder from falling into it.

## Topology Documents

Before each batch of pages, a topology document worked out what was genuinely new. The one covering `/cart`, `/player` and `/websites` opens by confirming via DOM diff that all three share the homepage's header and footer verbatim, then sorts every remaining section into three buckets: reuse unchanged, reuse with page-specific data, or build.

The consequence is a small component set behind a wide site. `StatsSection`, `DemoSection`, `FaqAccordion` and `ResourcesTabs` were each parameterised with their homepage content as the default value — so the pages that needed different content passed props, and the homepage kept working without being touched. Per-page accent colours (Easycart teal `#0E534C`, Easyplayer maroon `#940733`, Easypage burnt orange `#943F0C`) stayed inline hex rather than becoming global tokens, matching the convention already in the codebase.

## Site Map

- **Homepage** — hero, tool-suite grid, Wistia demo, integrations marquee, wall-of-love testimonial marquee, resources tabs, FAQ, CTA
- **Product pages** — Easycart, Easyplayer, Easypage, Easymail, Easylove, plus the legacy tools (Easycoffee, Easyfaq, Easylegal, Easycookie, Easyticker)
- **Features** — thirteen pages: one-click purchases, pricing models, checkout recovery, customer portal, digital downloads, gated content, global tax and invoices, QR-code tickets, sales automations, and more
- **Solutions** — twelve pages framed by what you sell (courses, ebooks, SaaS licences, events, subscriptions, Notion templates) or what you want (higher checkout conversion, automated sales, global selling, compliance)
- **Pricing** — a monthly/yearly toggle lifted into React context so the plan cards and the full comparison table switch together
- **Resources and legal** — blog, guides, case study, competitor comparison, contact, about, FAQ, and three legal documents behind one shared layout

## The Creator Dashboard

The second half of the project is the part behind the login: **29 routes** of the seller-facing app — products, orders, customers, discount codes, campaigns and their audiences, courses, testimonials, waitlists, automations, analytics, reports, partners, store settings, and the legacy tool editors.

The dashboard is a different design system from the marketing site — its own greys, its own 8px radii, its own inset-panel shell — so it got its own token extraction, pulled live from the authenticated app and written down as a utility-class-to-value map before anything was built. Every observed page was a fresh account, which made empty states the primary state to reproduce rather than an afterthought.

One decision from that build is representative. The analytics page draws its charts with Chart.js on a canvas; every series on a fresh account is flat at zero. So the rebuild draws an inline SVG — eight dashed gridlines and one horizontal stroke — and notes in a comment why a charting library was not worth shipping for a straight line. Matching a screenshot and matching an implementation are different goals, and the spec-driven approach makes it explicit which one is being chased.

## Build Characteristics

- **Server-first** — 29 of 194 components carry `"use client"`; everything else renders on the server
- **Lottie without the SSR crash** — the dotLottie player is a custom element that touches `window` on import, so it is imported dynamically inside a client effect and the poster image holds the layout until it mounts
- **No dependence on the origin** — ten batch scripts pull every image, icon, Lottie and font into `public/` (53 MB), so the rebuild has no live tether to the site it came from
- **Fonts self-hosted** — Borna as a local `woff2` pair through `next/font/local`, Geist alongside it
- **Typed design tokens** — the Easytools palette declared once in `globals.css` under Tailwind 4's `@theme inline`, with the radius scale derived from a single `--radius`
- **Standalone output** — `output: "standalone"` with a multi-stage Dockerfile and a compose file offering both production and dev services
- **CI as the gate** — GitHub Actions runs lint, typecheck and a full build on Node 24 for every push and pull request

The takeaway from building it: at this width, the leverage is not in writing components faster but in refusing to start one until the thing it must match has been measured, written down, and checked for what it *doesn't* need.
