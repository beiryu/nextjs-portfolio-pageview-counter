## Technology Stack

Next.js 16, React 19, TypeScript, Tailwind CSS 4, Framer Motion, HugeIcons, ESLint, Prettier, Vercel

## Overview

Duration: 5/2026 - 6/2026

scrape.ly sells web scraping infrastructure — scrapers, proxies, an API, prebuilt templates, and a store — to developers and data teams. The site is the pre-launch marketing surface for it: nineteen routes covering the product lines, the resources, the company, and the legal pages.

The dependency list is deliberately short — Next, React, Tailwind, one animation library, one icon set, and nothing else. There is no UI kit and no CSS-in-JS. Everything visual is built on a design system defined in one stylesheet and a set of layout primitives, which is what makes this one worth writing about: the interesting work is in the foundation rather than in the pages sitting on it.

## The Grid System

Every page is composed from two primitives, and the whole site inherits its rhythm from them.

`SiteGrid` establishes a twelve-column grid. `GridRow` then splits each row the same way every time — **two columns of decor, eight of content, two of decor** — as three components: a left `DecorCell`, a `ContentCell`, and a right `DecorCell`.

What makes it hold together is the CSS behind it. Below 48rem the grid is a plain twelve equal columns. Above it, the template becomes `1fr | gutter | 8 content columns | gutter | 1fr` — so the content band is a fixed measure and the fluid space is pushed into the outer margins, where it belongs. Rows use `align-items: stretch`, which is why the decorative side cells always match the height of whatever content sits between them.

The decor cells are then configurable rather than decorative-only:

- **`decor`** turns the side cells off entirely for full-bleed rows
- **`decorMerged`** fuses each pair of outer columns into a single tile per side, removing the seam between the twin cells
- **`decorGutter`** switches the inner gutter tile between its default and a 2×2 dot motif used beside the navigation

The result is an editorial, visibly-gridded layout — the kind that usually gets hand-built per page and drifts within a week — expressed as one row component that every page calls.

## Design Tokens

`globals.css` opens by declaring its own layer order, and then keeps to it:

1. **A primitive palette** of raw values, annotated as never to be referenced from JSX
2. **Semantic tokens** — `--color-page`, `--color-bg`, `--color-surface`, `--color-border` — mapped through Tailwind 4's `@theme inline` so they become utilities
3. **Typography, spacing, and radius scales** feeding `text-*`, `p-*`, and `rounded-*`
4. **Base styles** last

The discipline is the point: a component reaches for `bg-surface` or `border-border`, never a hex value, and never the primitive behind the token either. Retheming the site is an edit to the second layer, and nothing below it needs to be touched.

## Routing

Routes are organised with **App Router route groups** — `(marketing)`, `(products)`, `(resources)`, `(company)`, `(legal)` — so the URL structure stays flat while the source tree groups by concern.

`src/lib/routes.ts` is the counterpart to that on the link side:

- **A typed `ROUTES` map** mirroring the app directory, so no href is written as a bare string in a component
- **Path builders** — `templatePath()` and `apiPath()` compose URLs through a shared `slugify()` rather than each caller formatting its own
- **`legalTab()`** builds the query for a single legal page that switches between terms, privacy, refund, and SLA by tab, instead of four near-identical routes
- **A separate `EXTERNAL` map** for off-site destinations, each entry commented with which buttons use it

## The A/B Variant

The landing page ships in two versions — `landingA` at the root and `landingB` at `/landing-b` — with a shared `landing/` component folder and a small variant folder for each.

The B hero needs a different grid treatment from every other row on the site. Rather than threading a variant flag down through `SiteGrid` and `GridRow`, the stylesheet does it directly:

```css
.grid-row:has(.landing-b-hero) { /* … */ }
.grid-row:has(.landing-b-hero) .content-cell { /* … */ }
.grid-row:has(.landing-b-hero) .decor-cell { /* … */ }
```

The row reshapes itself because of what it contains. The layout primitives stay unaware that variants exist, and adding a third would not touch them either.

## Current State

This is a pre-launch build, and the repository is honest about it in a way worth repeating rather than glossing:

- The dynamic detail routes — `templates/[slug]`, `api/[slug]`, `integrations/[slug]`, `store/search/[slug]` — await their params and then render fixed content. They are complete visual shells with no data source behind them yet.
- `EXTERNAL` carries placeholder destinations, each marked in a comment to be swapped for the real URL when it exists.

Both are the right shape for the stage: the layout, the token system, and the page compositions are finished, and wiring them to a catalogue is a later job that will not disturb any of it.

What makes this one stand out from the other marketing builds is that almost none of the work is in the pages. It is in a grid you can describe in one sentence, a token layer with a rule about what may reference what, and a variant mechanism that adds nothing to the component API.
